# 설계 메모

## 판단의 순서

```
측정 ─▶ 피해자가 괴로운가? ─▶ (그렇다면) 범인은 누구인가? ─▶ 얼마나 세게? ─▶ 효과가 있었나?
```

| 단계 | 하는 일 | 코드 |
|---|---|---|
| 측정 | 시스템 CPU 정체율(PSI `some total` 의 증가량), 앞 프로그램이 CPU를 기다린 시간(`schedstat` 의 대기 시간 증가량) | `engine.rs` `measure` |
| 피해자 | 기다림 비율 = 기다린 시간 ÷ (쓴 시간 + 기다린 시간). 앞 프로그램이 거의 일하지 않으면(5% 미만) 0 | `measure` |
| 범인 | `yield` 목록, 또는 `auto` 일 때 코어를 `auto_hog_cpu`% 이상 `auto_hog_secs`초 동안 계속 쓴 프로세스 | `collect_targets` |
| 세기 | 단계 1~4 = 우선순위값 5/10/15/19 (`nice_target` 이 상한). 괴로움이 높으면 올리고, 낮으면 내리고, 그 사이는 유지 | `controller.rs` |
| 검증 | 가장 센 단계에서 `settle` 시간이 지나도 기다림이 처음의 70% 아래로 내려오지 않으면 `NoEffect`: 전부 원복하고 쉼 | `controller.rs` |

피해자를 모르면(앞 창을 알 수 없으면) 시스템 전체 정체율을 피해자의 대용으로 씁니다. 이때 `auto`는 꺼집니다.
앞 프로그램의 첫 측정에서는 변화율을 알 수 없으므로 괴로움을 0으로 둡니다. 시스템 전체 값으로 대신하면
"피해자 없이 범인을 탓하는" 일이 되기 때문입니다.

## 왜 세션 전체를 낮추나

커널의 스케줄러 autogroup 이 켜져 있으면(데스크톱 커널의 기본값) CPU는 먼저 **세션끼리** 똑같이 나뉘고,
그 안에서 프로세스끼리 나뉩니다. 이때 다른 세션에 있는 프로세스 하나의 `nice` 는 그 세션 안에서의 몫만 바꿀 뿐
세션 전체의 몫은 그대로입니다. 직접 잰 결과(코어 2개, 범인이 세션마다 하나씩, 단위 ms):

| | 앞 작업 걸린 시간 |
|---|---:|
| 범인 없음 | 160 |
| 범인 있음, 아무것도 안 함 | 491 |
| 범인의 `nice` 19 (프로세스만) | 395 |
| 범인 세션의 autogroup `nice` 19 | **125** |

그래서 범인이 다른 세션에 있고 그 세션에 보호 대상이 없으면 `/proc/<pid>/autogroup` 에 값을 써서 세션 전체를 낮춥니다.
같은 세션이면 프로세스 단위로 낮춥니다(앞 프로그램의 세션을 건드릴 수는 없으니까요).
`/proc/<pid>/autogroup` 에 쓰기가 막히면(권한 부족) 그 세션은 이후 프로세스 단위로만 다룹니다.

## 되돌리기 기록 (저널)

- 항목은 두 종류입니다: 프로세스(`task`) 또는 세션(`group`). 같은 대상은 하나의 항목만 갖습니다.
- 단계를 바꿀 때는 **새 값을 적은 기록을 먼저 저장**하고 나서 값을 바꿉니다. 그 사이에 죽어도 복구할 수 있게
  항목에 `previous_nice`(바로 앞 값)를 같이 적고, 복구는 현재 값이 "적용한 값" 또는 "바로 앞 값"일 때 우리 것으로 봅니다.
- 복구는 사용자가 그 사이에 바꾼 값(둘 중 어느 것도 아닌 값)을 건드리지 않습니다.
- 0.1 형식의 기록 파일도 읽습니다.

## 구조

```
main.rs        명령줄 (status / blame / doctor / run / restore)
engine.rs      판단 엔진. 한 번의 tick = 측정 → 피해자 → 범인 → 단계 → 적용/원복
controller.rs  피드백 제어기: 단계 올림/내림, 확인 횟수, 효과 검증 (시간 흐름만 알고 운영체제는 모름)
policy.rs      메모리 점수, EMA, 히스테리시스
provider.rs    운영체제와 맞닿는 유일한 경계 (Provider 트레이트)
proc.rs        /proc 읽기와 해석 (순수 함수 + 가짜 /proc 로 시험 가능)
journal.rs     되돌리기 기록 (원자적 쓰기, 프로세스/세션 두 종류)
foreground.rs  앞 창 알아내기 (xprop, 또는 foreground_cmd 의 출력)
config.rs      설정 해석
sys.rs         libc 호출 몇 개 (외부 라이브러리 없이 직접 연결)
```

제어기는 숫자와 시각만 받으므로 운영체제 없이 시험할 수 있고, 엔진은 `Provider`만 알기 때문에 가짜 운영체제로
"피해자가 괴로워지고 풀리는" 상황을 마음대로 만들 수 있습니다. 진짜 시스템 시험은 같은 엔진에 진짜 `LinuxProvider`를 끼우고
정체율과 앞 프로그램의 기다림 수치만 강제로 정합니다.

## 왜 이렇게 했나

- **피해자가 없으면 아무도 건드리지 않는다.** 바쁜 컴퓨터는 문제가 아닙니다. 누군가 기다리고 있는 것이 문제입니다.
- **효과를 스스로 검증한다.** 효과 없는 변경을 붙들고 있는 것이 이런 도구의 가장 흔한 실패입니다.
  측정에서도 프로세스 단위 조치가 효과가 없는 배치를 RamFlow가 3번 모두 알아채고 되돌렸습니다.
- **기록 먼저, 변경은 나중.** 순서가 반대면 그 사이에 죽었을 때 되돌릴 방법이 없습니다.
- **스레드 전부.** `setpriority(PID)`는 대표 스레드 하나만 바꿉니다. 여러 스레드 작업이 실제로 양보하려면 전부 바꿔야 합니다.
- **한가하면 아무것도 읽지 않는다.** 한가할 때는 작은 파일 3개(`meminfo`, `stat`, `pressure/*`)만 읽고, 프로세스 목록은 시스템 정체율이 `stall_gate`를 넘거나 되돌릴 게 남았을 때만 훑습니다.
- **메모리 문제로는 우선순위를 낮추지 않는다.** 메모리 부족에 `nice` 가 도움이 된다는 근거를 찾지 못했습니다. 메모리는 선택 기능인 정리(`trim_idle`)에만 쓰입니다.
- **외부 라이브러리 없음.** 필요한 libc 함수가 몇 개뿐이라 직접 연결했습니다.

## 메모리 압박 점수 (정리 기능용)

| 입력 | 0점 | 100점 | 가중치 |
|---|---|---|---|
| 사용 가능 메모리 비율 | 25% 이상 | 5% 이하 | 0.40 |
| PSI some (10초 평균) | 0% | 25% | 0.35 |
| PSI full (10초 평균) | 0% | 10% | 0.15 |
| 스왑 사용률 | 20% 이하 | 100% | 0.10 |

없는 센서는 빼고 나머지로 계산하고, EMA(0.4)로 부드럽게 한 뒤 히스테리시스와 `confirm` 번 연속 확인으로 "위험" 상태를 정합니다.

## 알려진 한계와 앞으로 할 일

1. 시험은 코어 2개짜리 가상머신 하나뿐입니다. `auto` 의 독차지 기준(35%/5초)은 이 구성을 염두에 두고 정했습니다.
2. cgroup v2 의 `cpu.weight` 를 쓰는 환경(systemd 사용자 슬라이스 등)에서의 동작은 시험하지 못했습니다.
3. 실제 브라우저·편집기·게임으로 앞 프로그램의 체감 지연을 재는 시험.
4. arm64 와 여러 배포판에서 시험.
5. 엔진과 화면을 유닉스 소켓으로 분리하고 트레이 화면 만들기.
