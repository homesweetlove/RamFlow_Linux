# RamFlow for Linux

[![English](https://img.shields.io/badge/Language-English-2F81F7)](README.md)
[![한국어](https://img.shields.io/badge/언어-한국어-2F81F7)](README.ko.md)

**지금 쓰고 있는 작업을 먼저 지켜주는** 리눅스용 자원 관리 도구입니다.
[윈도우판 RamFlow](https://github.com/homesweetlove/RamFlow)의 판단 방식을 리눅스에 맞게 다시 만들었습니다.

> RAM을 "비우는" 도구가 아닙니다. 리눅스는 남는 메모리를 캐시로 이미 잘 쓰고 있어서, 억지로 비우면 오히려 느려집니다.
> 이 도구가 하는 일은 **누구에게 먼저 CPU를 줄지 정하는 것**이고, **실제로 누군가 느려지고 있을 때만** 합니다.

## 핵심 아이디어: 피해자를 먼저 찾고, 그다음 범인을 찾는다

대부분의 도구는 "컴퓨터가 바쁘면" 우선순위를 낮춥니다. 하지만 컴퓨터가 바쁜 것은 문제가 아닙니다.
문제는 **내가 쓰는 프로그램이 CPU 차례를 기다리는 것**입니다. 그래서 RamFlow는 거꾸로 생각합니다.

1. **피해자 먼저.** 매번 앞에 있는 프로그램이 "CPU를 쓰고 싶었던 시간" 중 얼마를 **차례를 기다리느라** 보냈는지 잽니다
   (`/proc/<pid>/schedstat`). 컴퓨터가 100% 바빠도 앞의 프로그램이 멀쩡하면 아무도 건드리지 않습니다.
2. **그다음 범인.** 피해자가 괴로울 때만 누구를 늦출지 찾습니다. 직접 적어준 작업(`yield`), 또는 `auto = true`면
   **코어를 오래 독차지하는 프로그램을 목록 없이 스스로** 찾습니다.
3. **단계별 조절.** 처음엔 살짝(우선순위값 10), 피해자가 계속 괴로우면 한 단계씩 더(15, 19), 괴로움이 사라지면 다시
   한 단계씩 풀어줘서(배경 작업이 쓸 수 있는 만큼 쓰도록) 합니다. 앞의 프로그램이 조용해지면 전부 원래대로 돌립니다.
4. **자기 일을 스스로 검증.** 가장 센 단계에서도 피해자의 기다림이 줄지 않았다면 그 조치는 쓸모가 없었던 것입니다.
   그러면 **전부 원래대로 돌리고, 그 사실을 알리고, 한동안 쉽니다.** 효과 없는 변경을 붙들고 있지 않습니다.
5. **리눅스가 실제로 CPU를 나누는 방식을 압니다.** 요즘 데스크톱 커널은 로그인 세션마다 CPU를 똑같이 나눕니다
   (autogroup). 그래서 다른 세션에 있는 프로세스 하나의 우선순위를 낮춰도 거의 효과가 없습니다.
   RamFlow는 범인이 **다른 세션**에 있으면 그 **세션 전체**를 낮춥니다. 단, 그 세션에 보호 대상이 없을 때만입니다.

이 조합을 아무도 하지 않았다고 주장하지는 않습니다(문헌을 조사하지 않았습니다). 제가 아는 도구 중에 이렇게 하는 것을
못 봤을 뿐이고, 대신 **실제로 효과가 있다**는 것은 [측정](#효과가-있나)으로 보여드립니다.

## 설치

러스트(cargo)가 있으면 됩니다. ([rustup.rs](https://rustup.rs))

```bash
git clone https://github.com/homesweetlove/RamFlow_Linux
cd RamFlow_Linux
cargo build --release
sudo ./install.sh            # 서비스를 바로 켜려면: sudo ./install.sh --enable
ramflow doctor               # 이 컴퓨터에서 무엇이 되는지 점검
```

제거: `sudo ./uninstall.sh` (먼저 서비스를 멈추면서 바꾼 것을 모두 되돌립니다. 설정까지 지우려면 `--purge`)

## 사용법

```bash
ramflow blame                # 3초 재서 "누가 기다리고, 누가 독차지하는지"와 RamFlow가 무엇을 할지 보여줌
ramflow status               # 지금 메모리·CPU 압박 상태 한 번 보기
ramflow doctor               # 쓸 수 있는 기능 점검
ramflow run                  # 예행연습으로 감시 시작 (아무것도 바꾸지 않음)
sudo ramflow run --apply     # 실제로 적용
sudo ramflow restore         # 갑자기 꺼져서 남은 변경을 모두 되돌리기
```

`/etc/ramflow/ramflow.conf` ([전체 예시](packaging/ramflow.conf.example)):

```ini
dry_run = true                  # 먼저 로그만 지켜보세요
auto = true                     # 목록 없이도 CPU 독차지하는 프로그램을 스스로 찾음 (앞 창을 알아야 함)
yield = /usr/bin/ffmpeg         # 그리고/또는 언제든 양보해도 되는 작업을 직접 적기
protect = comm:obs              # 절대 건드리지 않을 것
foreground_cmd = hyprctl activewindow -j | jq .pid   # 웨일랜드: 앞 창의 pid 를 출력하는 명령
```

X11에서는 앞 창을 자동으로 알아냅니다(`xprop`). 웨일랜드에서는 `foreground_cmd`에 앞 창의 pid를 출력하는 명령을 적어 주세요.
앞 창을 모르더라도 `yield` 목록으로는 동작합니다. 이때는 시스템 전체의 CPU 정체율(PSI)로 판단하며,
`auto`는 앞 창을 알아야 하므로 꺼진 채로 있습니다.

## 안전장치

| 상황 | 동작 |
|---|---|
| 처음 시작 | 예행연습. `--apply` 또는 `dry_run = false` 라야 실제로 바꿈 |
| 아무도 괴롭지 않을 때 | 컴퓨터가 아무리 바빠도 아무것도 건드리지 않음 |
| 바꾸기 전 | 원래 값을 디스크에 원자적으로 **먼저** 적음. 적지 못하면 바꾸지 않음 |
| 앞에 있는 프로그램 | 그 프로세스, 거기서 시작된 것들, 같은 이름의 짝 프로세스, 그리고 그것들이 속한 세션은 절대 낮추지 않음 |
| 보호 대상(sshd, 내가 쓰는 셸 등)과 같은 세션 | 세션 전체는 낮추지 않고, 프로세스 하나만 낮춤 |
| 낮춰둔 작업으로 사용자가 이동 | 컴퓨터가 아직 바빠도 즉시 원복 |
| 낮춰도 도움이 안 됨 | 전부 원복하고 알림을 남기고, 한동안 쉬었다가 다시 시도 |
| 바쁜 상태 끝 / `SIGTERM` | 전부 원복 |
| 갑작스런 종료(`kill -9`, 정전) | 다음 시작 때 또는 `ramflow restore`가 기록을 보고 원복. 단계를 바꾸던 도중에 죽었어도 마찬가지 |
| 그 사이 사용자가 값을 바꿈 | 사용자 값을 존중. 절대 덮어쓰지 않음 |
| PID 재사용 | PID와 **시작 시각**으로 구분 |
| 재부팅 | 이전 부팅의 기록은 버림 |
| 되돌릴 권한이 없음 | `--apply` 거부 (낮추기는 쉽지만 `CAP_SYS_NICE` 없이는 되돌릴 수 없어서) |
| 기본 보호 목록 | systemd, sshd, Xorg, gnome-shell, pipewire … 목록에 적거나 "독차지"해도 건드리지 않음 |
| `auto` | 기본 꺼짐. 시스템 계정(uid 1000 미만)은 제외. 앞 창을 알아야 동작 |

리눅스의 우선순위값(nice)은 **스레드마다** 따로입니다. 그래서 작업의 모든 스레드를 바꾸고, 원복할 때는 우리가 정한 값 그대로인 스레드만 되돌립니다.

## 선택 기능: 오래 안 쓴 큰 앱 메모리 정리 (`trim_idle`, 기본 꺼짐)

메모리가 **위험**할 때, 한동안 가만히 있던 큰 앱(앞에 있는 창 제외)의 쓰지 않는 메모리를 커널에 돌려달라고 요청합니다
(`process_madvise(MADV_PAGEOUT)`, 리눅스 5.10 이상). 앞 창을 알아야 하고 스왑/zram이 있으면 효과가 더 좋습니다.
한 번에 프로세스 하나씩, 쉬는 시간을 둡니다. 메모리 문제만으로는 우선순위를 절대 낮추지 않습니다(메모리에는 우선순위가 도움이 된다는 근거가 없습니다).

## 효과가 있나?

[`scripts/latency-bench.py`](scripts/latency-bench.py)는 **피해자**(내가 쓰는 프로그램을 대신하는 CPU를 많이 쓰는 파이썬 프로세스)와
**범인** 4개(코어 수의 2배)를 실제 프로세스와 실제 프로그램으로 돌려 잽니다. 흉내 낸 것은 없습니다.
네 가지 방식 — *없음*, *프로세스만*(`nice` 그대로), *세션 단위*(기본), *자동*(목록 없음) — 을 3바퀴 번갈아 돌렸고,
범인이 놓인 방식을 세 가지로 나눴습니다. 가운데값입니다. "긴 작업"은 피해자의 약 150ms짜리 일 한 조각이며, 범인이 없을 때는 154~177ms 걸립니다.
원본 출력: [`docs/evidence/2026-11-18-v0.2-effect/`](docs/evidence/2026-11-18-v0.2-effect/).

진짜 크롬으로 잰 결과(5블록, 검색·정렬 p95 약 −75~80%, 자료 전부 공개): [`docs/REAL_CHROME_STUDY.ko.md`](docs/REAL_CHROME_STUDY.ko.md).

**범인이 여러 세션에 흩어진 경우** (서로 상관없는 앱·서비스 여러 개 — 그냥 `nice`로는 안 되는 경우)

| 방식 | 긴 작업 | 없음 대비 | 짧은 일 p95 | 범인이 쓴 CPU |
|---|---:|---:|---:|---:|
| 없음 | 378 ms | — | 2.80 ms | 코어 1.73 / 2 |
| 프로세스만 (`nice` 그대로) | 400 ms | **+6 %** (도움 안 됨 — RamFlow가 설계대로 3번 스스로 되돌림) | 2.83 ms | 1.74 |
| **세션 단위** | **157 ms** | **−59 %** | 2.43 ms | 1.62 (−6 %) |
| **자동** (목록 전혀 없음) | **154 ms** | **−59 %** | 2.57 ms | 1.58 (−9 %) |

**범인이 앞 프로그램과 같은 세션에 있는 경우** (터미널 하나에서 전부 시작한 경우)

| 방식 | 긴 작업 | 없음 대비 | 범인이 쓴 CPU |
|---|---:|---:|---:|
| 없음 | 397 ms | — | 1.73 |
| 프로세스만 | 192 ms | −52 % | 1.58 (−8 %) |
| 세션 단위 (같은 세션이라 프로세스만으로 대신함) | 173 ms | −57 % | 1.61 (−7 %) |
| 자동 | 160 ms | −60 % | 1.56 (−10 %) |

**범인들이 앞 프로그램과 다른 세션 한 곳에 모여 있는 경우** — 커널의 세션 나누기가 이미 앞 프로그램을 지켜줍니다
(범인이 없을 때 154ms, 있을 때 167ms로 거의 안 느려짐). RamFlow도 기준을 넘지 않아 (거의) 아무것도 하지 않았고,
이 경우의 차이는 잡음 수준이라 **효과로 주장하지 않습니다.**

이 결과가 보여주는 것과 보여주지 못하는 것:

- 진짜 피해자가 있을 때 긴 작업이 **컴퓨터가 한가할 때와 거의 같은 속도**로 돌았고, 대가는 범인의 처리량 약 6~10%입니다
  (우선순위는 남는 CPU를 놀리지 않아서 범인들도 남는 만큼은 계속 씁니다).
- 두 가지 설계 결정이 측정으로 정당화됩니다. **세션 전체 낮추기**(프로세스만으로는 세션을 건너 효과가 없음)와
  **스스로 검증**(쓸모없던 조치를 알아채고 되돌림).
- 짧고 잦은 일(10ms마다 1.5ms)은 얻는 게 별로 없습니다. 리눅스가 원래 잠자는 쪽을 챙겨 줍니다
  (방식 간 p95 차이 ±10%는 잡음이고, 한 바퀴만 보면 1.6~6.3ms로 흔들렸습니다).
- 한계: 코어 2개짜리 가상머신 한 대, 커널 6.18, 극단적인 인위적 부하, 파이썬 측정기 — 실제 브라우저나 편집기가 아닙니다.
  `auto`의 독차지 기준(코어의 35%, 5초. 컴퓨터가 꽉 찼을 때는 15%)은 코어 2개짜리 가상머신과 인공 범인으로 정했습니다. cgroup v2의 `cpu.weight`를 쓰는 환경,
  다른 구조의 CPU, 웨일랜드 화면 관리자는 시험하지 못했습니다. 윈도우판 README의 수치는 윈도우에서 잰 것이라 여기에 적용되지 않습니다.

## 검증

`cargo test`는 시험 131개를 돌립니다. 단위 시험 111개(제어기, 가짜 운영체제 위의 엔진, 기록 파일 형식과 중간에 죽는 경우, 가짜 `/proc`)와
**진짜 프로세스·진짜 프로그램**을 쓰는 시험 20개입니다. 모든 스레드를 낮추고 되돌림, 진짜 세션을 낮추고 되돌림,
기록만으로 갑작스런 종료 복구, 피해자 없이 바쁘기만 한 컴퓨터는 가만히 둠, 앞 프로그램은 절대 안 건드림,
사용자가 바꾼 스레드는 그대로 둠, 독차지하는 프로그램 자동 발견, `SIGTERM` 때 원복, `kill -9` 뒤 복구, 예행연습은 아무것도 안 바꿈.
5번 반복해서 한 번도 실패하지 않았습니다. `cargo fmt --check`와 `clippy -D warnings`도 깨끗합니다.

## 한계

- 아직 화면(GUI/트레이)이 없습니다 — 명령줄과 서비스만.
- 앞 창을 모르면(`foreground_cmd` 없는 웨일랜드) 시스템 전체의 정체율로만 판단하고, 어느 프로그램을 쓰는지 알 수 없어서 `auto`와 `trim_idle`은 꺼진 채로 있습니다.
- 세션 전체를 낮추면 그 세션의 다른 구성원(같은 세션의 셸 등)도 느려집니다. 보호 대상이 들어 있는 세션은 통째로 낮추지 않습니다.
- 우선순위(nice/autogroup)만 씁니다. cgroup `cpu.weight`, 효율 코어 배치, 페이지파일 같은 것은 없습니다.
- x86_64, 커널 6.18에서만 시험했습니다. 서비스 파일은 문법만 점검했고 진짜 systemd로 부팅해 보지는 않았습니다.
- `process_madvise`는 진짜 프로세스에서 성공하는 것까지 확인했지만, 이 컴퓨터에는 스왑이 없어서 실제 RAM이 줄어드는 것은 못 봤습니다.
