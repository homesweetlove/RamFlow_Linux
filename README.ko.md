# RamFlow for Linux

[![English](https://img.shields.io/badge/Language-English-2F81F7)](README.md)
[![한국어](https://img.shields.io/badge/언어-한국어-2F81F7)](README.ko.md)

**지금 쓰고 있는 작업을 먼저 지켜주는** 리눅스용 자원 관리 도구입니다.
[윈도우판 RamFlow](https://github.com/homesweetlove/RamFlow)의 판단 방식을 리눅스에 맞게 다시 만들었습니다.

컴퓨터가 바빠지면(CPU가 꽉 차거나 메모리가 모자라면), 사용자가 **직접 적어준** 배경 작업(영상 변환, 컴파일 등)의 우선순위만 낮춰서 지금 쓰는 앱이 버벅이지 않게 합니다. 바쁜 상태가 끝나면 **바꾼 것을 전부 원래대로** 돌려놓습니다.

> RAM을 "비우는" 도구가 아닙니다. 리눅스는 남는 메모리를 캐시로 이미 잘 쓰고 있어서, 억지로 비우면 오히려 느려집니다.
> 이 도구가 하는 일은 **누구에게 먼저 자원을 줄지 정하는 것**입니다.

## 특징

- **가볍습니다.** 실행 파일 약 540 KiB, 한가할 때 상주 메모리 약 2.4 MiB, CPU 사용 0%. 외부 라이브러리가 하나도 없고 실행 중 스레드도 1개입니다.
- **안전합니다.** 기본은 **예행연습**(아무것도 안 바꾸고 무엇을 할지만 알려줌). 아래 [안전장치](#안전장치)를 보세요.
- **정확하게 판단합니다.** 커널의 압박 정보(PSI)를 써서, 메모리가 "적다"가 아니라 "실제로 작업이 멈칫하고 있다"를 기준으로 삼습니다.

## 설치

러스트(cargo)가 있으면 됩니다. ([rustup.rs](https://rustup.rs))

```bash
git clone https://github.com/homesweetlove/RamFlow-Linux
cd RamFlow-Linux
cargo build --release
sudo ./install.sh            # 서비스를 바로 켜려면: sudo ./install.sh --enable
ramflow doctor               # 이 컴퓨터에서 무엇이 되는지 점검
```

제거: `sudo ./uninstall.sh` (먼저 서비스를 멈추면서 바꾼 것을 모두 되돌립니다. 설정까지 지우려면 `--purge`)

## 사용법

```bash
ramflow status               # 지금 메모리·CPU 압박 상태 한 번 보기
ramflow doctor               # 쓸 수 있는 기능 점검
ramflow run                  # 예행연습으로 감시 시작 (아무것도 바꾸지 않음)
sudo ramflow run --apply     # 실제로 적용
sudo ramflow restore         # 혹시 남은 변경이 있으면 모두 원래대로
```

### 설정

`/etc/ramflow/ramflow.conf` (예시: [packaging/ramflow.conf.example](packaging/ramflow.conf.example))

```ini
dry_run = true                  # 먼저 로그만 지켜보세요
yield = /usr/bin/ffmpeg         # 바빠지면 양보할 작업 (전체 경로 또는 comm:이름)
yield = comm:cc1plus
protect = comm:obs              # 절대 건드리지 않을 프로그램
```

**적어준 프로그램만** 건드립니다. 적지 않은 프로그램은 어떤 경우에도 그대로입니다.

## 안전장치

| 상황 | 동작 |
|---|---|
| 처음 켰을 때 | 예행연습. `--apply` 하거나 설정에서 `dry_run = false` 로 바꿔야 적용됩니다 |
| 바꾸기 전에 | 원래 값을 디스크에 **먼저** 기록합니다. 기록에 실패하면 아무것도 바꾸지 않습니다 |
| 앞에 있는 창의 프로그램 | 그 프로그램, 그 프로그램이 실행한 하위 프로그램, 같은 이름의 형제 프로그램은 건드리지 않습니다 (X11) |
| 양보 중인 작업으로 사용자가 전환 | 바쁜 상태여도 즉시 원래 우선순위로 돌려줍니다 |
| 바쁜 상태가 끝남 / 서비스 정지(SIGTERM) | 전부 원래대로 되돌립니다 |
| 갑자기 죽었을 때(kill -9, 정전) | 다음 시작 때, 또는 `ramflow restore` 로 기록을 보고 되돌립니다 |
| 사용자가 직접 값을 바꿨을 때 | 사용자의 값을 존중해서 덮어쓰지 않습니다 |
| 프로세스가 끝나고 번호가 재사용됐을 때 | (번호 + 시작 시각)으로 구별해서 엉뚱한 프로세스를 건드리지 않습니다 |
| 재부팅 후 | 이전 부팅의 기록은 버립니다 |
| 되돌릴 권한이 없을 때 | 적용 자체를 거부합니다 (우선순위는 올리긴 쉬워도 낮춘 걸 되돌리려면 root 권한이 필요하기 때문) |
| 기본 보호 목록 | systemd, sshd, Xorg, gnome-shell, pipewire 등은 설정에 적어도 건드리지 않습니다 |

리눅스는 우선순위(nice 값)를 **스레드마다** 따로 가집니다. 대표 스레드 하나만 바꾸면 여러 스레드로 일하는 작업은 거의 그대로이므로, 모든 스레드를 바꾸고 되돌릴 때도 모든 스레드를 확인합니다.

## 선택 기능: 오래 안 쓴 큰 앱의 메모리 정리

`trim_idle = true` 로 켜면(기본 꺼짐), 메모리가 **위험** 수준일 때 한참 가만히 있던 큰 앱의 쓰지 않는 메모리를 커널에 돌려달라고 요청합니다(`process_madvise`). 윈도우판의 App Nap과 비슷합니다.

- 앞에 있는 창을 알아낼 수 있어야 동작합니다(X11). **Wayland는 구조상 다른 프로그램의 창을 볼 수 없어서 쓸 수 없습니다.** 모를 때는 "아무도 안 쓴다"로 보지 않고 아예 동작하지 않습니다.
- 스왑이나 zram이 있어야 효과가 큽니다. 없으면 파일 캐시 정도만 회수됩니다.
- 일반 사용자 앱(uid 1000 이상)이고 메모리를 200 MiB 이상 쓰는 것만 대상이며, 한 번에 하나씩, 10분 쉬었다가 다시 합니다.
- 정리된 앱은 다시 쓸 때 잠깐 느려질 수 있습니다. 그게 이 기능의 대가입니다.

## 실측한 자체 사용량

이 저장소를 만든 리눅스 환경(CPU 2코어, 메모리 8 GB, 프로세스 68개)에서 릴리스 빌드로 직접 잰 값입니다.

| 항목 | 값 |
|---|---|
| 실행 파일 크기 | 540 KiB |
| 한가할 때 (2초 간격, 20초) | 상주 2.4 MiB · CPU 0 tick · 스레드 1개 |
| CPU 100% 부하 중 양보 적용 (0.5초 간격, 20초) | 상주 2.4 MiB · CPU 평균 0.15% |

**윈도우판 README의 "응답 지연 45~49% 감소"는 윈도우에서 잰 값이며, 리눅스판에는 해당하지 않습니다.** 리눅스판의 효과 측정은 아직 하지 않았습니다.

## 검증

`cargo test` 로 96개 시험을 돌립니다.

- 판단·설정·저널·측정 읽기 등 단위 시험 80개 (가짜 `/proc` 폴더 포함)
- **실제 프로세스와 실제 실행 파일**로 하는 시험 16개: 여러 스레드가 모두 낮아지고 모두 돌아오는지, 저널만으로 강제 종료에서 복구되는지, 앞 창 프로세스는 건드리지 않는지, 사용자가 바꾼 스레드는 그대로인지, `SIGTERM`으로 멈추면 원복되는지, `kill -9` 뒤 `ramflow restore` 로 복구되는지, 예행연습이 정말 아무것도 안 바꾸는지
- 서식 검사, `clippy`(경고를 오류로 취급), 서비스 파일 `systemd-analyze verify`, 설치·제거 스크립트 왕복 시험은 이 환경에서 직접 돌려 통과했고, 같은 내용이 GitHub Actions 자동 검증으로도 설정돼 있습니다

## 아직 안 되는 것 / 한계

- 화면(GUI)과 트레이 아이콘이 없습니다. 지금은 명령줄과 서비스뿐입니다.
- 앞 창 보호는 X11만 됩니다. Wayland에서는 "양보할 작업을 직접 적는 방식"이 유일한 보호 장치입니다. (그래서 적지 않은 건 안 건드리게 만들었습니다)
- 전체화면 감지, CPU 효율 코어 선택, 가상 메모리(Pagefile) 설정에 해당하는 기능은 아직 없습니다.
- x86_64 리눅스(커널 6.18)에서만 시험했습니다. 다른 구조(arm64 등)와 다른 배포판은 시험하지 못했습니다.
- 서비스 파일은 `systemd-analyze verify`로 문법만 확인했고, 이 환경에서는 systemd로 실제 부팅·실행해 보지 못했습니다.
- `process_madvise` 호출은 실제 프로세스에 성공하는 것까지 확인했지만, 이 환경에는 스왑이 없어서 메모리가 실제로 줄어드는 효과는 확인하지 못했습니다.
